# Отчёт по узким местам миграции на микросервисную архитектуру

Данный документ содержит анализ потенциальных узких мест при миграции с текущей монолитной архитектуры (Excel, 1С файловый, файловый сервер) на целевую микросервисную архитектуру (Spring Boot, Kubernetes, PostgreSQL).

---

## Контекст миграции

### Текущее состояние (As-Is)

| Компонент                 | Технология                      | Проблемы                             |
| ------------------------- | ------------------------------- | ------------------------------------ |
| Хранение данных пациентов | Excel на FileServer             | Нет разграничения доступа, дубликаты |
| Бухгалтерия               | 1С:Бухгалтерия (файловый режим) | Ограниченный аудит                   |
| Склад                     | 1С:Торговля и склад             | Интеграция через OLE                 |
| Касса                     | ККМ (TCP/IP + OLE)              | Дублирование в Excel                 |
| Почта                     | Exchange Server                 | Нет контроля конфиденциальных данных |

### Целевое состояние (To-Be)

| Компонент   | Технология                      | Назначение                          |
| ----------- | ------------------------------- | ----------------------------------- |
| Backend     | Java, Spring Boot, Spring Cloud | Микросервисы                        |
| Оркестрация | Kubernetes                      | Масштабирование, отказоустойчивость |
| IAM         | Keycloak                        | RBAC/ABAC, OAuth2/OIDC              |
| OLTP        | PostgreSQL                      | Транзакционные данные               |
| OLAP        | ClickHouse                      | Аналитика                           |
| Секреты     | HashiCorp Vault                 | Ключи шифрования                    |
| Логирование | Elastic                         | Аудит операций                      |
| ETL         | Apache Airflow                  | Пайплайны анонимизации              |

### Критические ограничения

- **Сроки**: пара месяцев (недостаточно для полной реализации)
- **Ресурсы**: ограниченная команда разработчиков
- **Требования**: Privacy by Design, соответствие 152-ФЗ
- **Бизнес**: непрерывность работы клиники

## Выявленные узкие места

### 1. ИНФРАСТРУКТУРА

| Проблема                                     | Описание                                                                                                | Влияние                                           |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| **Недостаточные ресурсы для Kubernetes**     | Для production-кластера K8s требуется минимум 3 master + 3 worker nodes с достаточным CPU/RAM           | Высокое — невозможность запуска микросервисов     |
| **Отсутствие dev/staging окружений**         | Текущая инфраструктура не предусматривает отдельных окружений для разработки и тестирования             | Среднее — риск внедрения непротестированного кода |
| **Ограниченная пропускная способность сети** | Микросервисная архитектура генерирует значительно больше сетевого трафика (inter-service communication) | Среднее — возможная деградация производительности |

### 2. ПРОГРАММНОЕ ОБЕСПЕЧЕНИЕ

| Проблема                             | Описание                                                                                              | Влияние                                          |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| **Сложность интеграции с legacy 1С** | 1С использует OLE/COM для интеграции, что несовместимо с контейнеризацией                             | Высокое — блокирует миграцию финансового контура |
| **Новый стек технологий**            | Spring Cloud, Kubernetes, PostgreSQL — требуют экспертизы, которая есть только у 1 человека в команде | Высокое — риск ошибок архитектуры + bus factor   |
| **Риск снижения производительности** | Микросервисы добавляют latency из-за сетевых вызовов, сериализации, API Gateway                       | Среднее — может влиять на UX                     |

### 3. ИНТЕГРАЦИЯ

| Проблема                                                 | Описание                                                           | Влияние                        |
| -------------------------------------------------------- | ------------------------------------------------------------------ | ------------------------------ |
| **Интеграция новых сервисов и внешней лабораторией**     | Лаборатория работает с собственным API                             | Среднее — требует адаптеров    |
| **Настройка API Gateway и межсервисного взаимодействия** | Service mesh, circuit breakers, retry policies — сложная настройка | Среднее — влияет на надёжность |

### 4. ПЕРСОНАЛ

| Проблема                     | Описание                                                                            | Влияние                       |
| ---------------------------- | ----------------------------------------------------------------------------------- | ----------------------------- |
| **Недостаток разработчиков** | MVP архитектура требует больше ресурсов, чем доступно (отмечено в документации)     | Критическое — срыв сроков     |
| **Сопротивление изменениям** | Сотрудники, работавшие с Excel и 1С, могут сопротивляться переходу на новые системы | Среднее — влияет на внедрение |

### 5. ПРОЦЕССЫ

| Проблема                        | Описание                                                                             | Влияние                                 |
| ------------------------------- | ------------------------------------------------------------------------------------ | --------------------------------------- |
| **Отсутствие CI/CD пайплайнов** | Без автоматизации сборки и деплоя микросервисная архитектура неуправляема            | Критическое — невозможность релизов     |
| **Сжатые сроки**                | «Пара месяцев» — недостаточно для полноценной миграции с соблюдением всех требований | Критическое — либо сроки, либо качество |
| **Недостаточное тестирование**  | Распределённые системы требуют интеграционного, нагрузочного и contract testing      | Высокое — дефекты в production          |

### 6. ДАННЫЕ

| Проблема                                            | Описание                                                                   | Влияние                                      |
| --------------------------------------------------- | -------------------------------------------------------------------------- | -------------------------------------------- |
| **Миграция из Excel в PostgreSQL**                  | Структурирование неформализованных данных, создание схемы БД, ETL-процессы | Критическое — без данных система бесполезна  |
| **Качество исходных данных**                        | Дубликаты, неполные записи, несогласованность форматов в Excel-файлах      | Высокое — «мусор на входе — мусор на выходе» |
| **Обеспечение целостности при параллельной работе** | В переходный период данные будут изменяться в обеих системах               | Критическое — рассинхронизация               |

## Рекомендации по устранению узких мест

### Приоритет 1: КРИТИЧЕСКИЕ

| №   | Проблема                 | Рекомендация                                                                                                             | Метрика успеха                       |
| --- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------ |
| 1.1 | Сжатые сроки             | **Фазовый подход**: выделить MVP-scope (запись на приём + профили), остальное — последующие итерации                     | Согласованный scope с бизнесом       |
| 1.2 | Недостаток разработчиков | **Аутсорс/аутстафф**: привлечь 2-3 senior-разработчиков с опытом Spring Cloud и K8s на время проекта                     | Укомплектованная команда             |
| 1.3 | Миграция данных из Excel | **Data migration sprint**: отдельный этап с очисткой данных, маппингом, валидацией. Использовать Apache Airflow          | Все данные в PostgreSQL с валидацией |
| 1.4 | Отсутствие CI/CD         | **Настройка pipeline**: GitLab CI / GitHub Actions + ArgoCD для K8s. Минимальный набор: build → test → deploy to staging | Автоматический деплой в staging      |

### Приоритет 2: ВЫСОКИЕ

| №   | Проблема                  | Рекомендация                                                                                                                     | Метрика успеха                   |
| --- | ------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| 2.1 | Недостаточные ресурсы K8s | **Managed Kubernetes**: использовать облачный K8s (Yandex Cloud, VK Cloud) для MVP, затем on-premise                             | Работающий кластер               |
| 2.2 | Качество исходных данных  | **Data profiling**: провести анализ качества данных в Excel (дубликаты, пропуски). Автоматизировать очистку                      | Data quality report              |
| 2.3 | Обучение персонала        | **Внутренние воркшопы**: 2-3 сессии по Spring Boot и K8s basics. Парное программирование с экспертами                            | Команда пишет код самостоятельно |
| 2.4 | Интеграция с 1С           | **API-adapter**: Найти готовое решешение или создать REST API wrapper над 1С (через COM+ или web-сервисы 1С). Изолировать legacy | Работающий адаптер               |
| 2.5 | Тестирование              | **Минимальный тест-сьют**: unit tests, integration tests для критических flows, contract tests для API                           | Автоматические тесты в CI        |

### Приоритет 3: СРЕДНИЕ

| №   | Проблема                         | Рекомендация                                                                                     | Метрика успеха                                   |
| --- | -------------------------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------ |
| 3.1 | Dev/staging окружения            | **Environment parity**: создать staging-окружение, максимально близкое к production              | Staging с реальными (анонимизированными) данными |
| 3.2 | Сетевая производительность       | **Service mesh**: внедрить Istio/Linkerd для управления трафиком, retry, circuit breaker         | P99 latency < 200ms                              |
| 3.3 | Интеграция с ККМ                 | **Adapter service**: отдельный микросервис-адаптер для ККМ с очередью сообщений (RabbitMQ/Kafka) | Транзакции ККМ в новой системе                   |
| 3.4 | Сопротивление изменениям         | **Change management**: демо новой системы, обучение пользователей, поддержка на старте           | Пользователи работают в новой системе            |
| 3.5 | Производительность микросервисов | **Caching и оптимизация**: Redis для кэширования, connection pooling, async где возможно         | Response time в норме                            |

## Заключение

Миграция на микросервисную архитектуру — комплексная задача с множеством потенциальных узких мест. Наиболее критичные области:

1. **Данные** — миграция из Excel требует тщательной подготовки и валидации
2. **Процессы** — без CI/CD и адекватных сроков проект обречён на провал
3. **Персонал** — недостаток ресурсов и компетенций нужно закрывать очень быстро
